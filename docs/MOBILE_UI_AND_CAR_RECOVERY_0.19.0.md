## Request and design

The user reported cramped, clumsy planning on a phone and asked for another UI pass informed by leading map apps. The user also reported that location reverts while connected to Android Auto and returns to the simulated location after Wi-Fi is manually disabled, with several reconnection attempts.

The design follows a visible sequence: choose places, review the plan, explicitly Start. Full-width search fields and nearby results take priority over secondary controls. A Map / Edit plan control preserves the draft while making the map usable. The itinerary follows place entry and results; its detailed controls can be collapsed. The planner uses one scroll viewport, including its stop list and search results, with drag-edge scrolling preserved. Save and Start remain separate and unfinished entries continue to block Start from every entry point. Offline microphones continue to fill editable text without interpretation or hosted processing.

While the keyboard is visible, the planner keeps its active input, microphone, inline Clear, matching places, compact simulation status and guarded primary action. Map, Done and Setup remain reachable; closing the keyboard restores the mode selector, other field and secondary controls. Focus changes preserve editable text and avoid erasing another field's results. Long primary labels are limited to two lines; secondary footer buttons have equal widths, spacing and bounded wrapping.

Keyboard search uses one line for editable place text and compact result rows with at least 56dp touch height. Place names and addresses retain separate readable lines; redundant result headings, decorative pins and distance labels yield space to the active field and first result. Saved matches use the same compact spacing, retaining their bookmark and full-name accessibility description. Normal result detail returns after the keyboard closes. Footer spacing and the map gap also tighten while searching.

Reference patterns: [Google Maps destination and trip selection](https://support.google.com/maps/answer/10271256), [Android secondary content in bottom sheets](https://developer.android.com/develop/ui/compose/quick-guides/content/create-bottom-sheet), and [Android minimum 48dp touch targets](https://support.google.com/accessibility/android/answer/7101858). These inform the changes; a visual resemblance does not establish usability on the user's phone.

The same sequence appears in [Waze's documented search flow](https://support.google.com/waze/answer/6262563?hl=en): type or speak, select a result, review routes, then explicitly begin. Waze also puts saved places near search. [Apple Maps documents adding and reordering stops before Go](https://support.apple.com/en-mide/guide/iphone/iph837d13d03/27/ios/27), with active-route additions reached through a route card. Applied here, these patterns favor visible Saved controls beside the field, results before itinerary details, a reversible map/plan transition and an explicit Start. This is a design inference from documented interactions, not a comparative user study or a claim that every interaction in those apps was reproduced.

## Android Auto: evidence and boundaries

The current service emits to GPS, network and Google fused location. Before this change its watchdog inspected only cached GPS, did not actively recover from observed real-location leakage, and did not consistently retry failed fused mock-mode activation. Those are source-confirmed defects independent of the unverified cause in the user's car.

Wireless Android Auto uses Wi-Fi. Disabling Wi-Fi may fix the symptom by ending projection. This is a hypothesis, not proof that Wi-Fi scanning is the source of the real location. Car hardware can supply location to supported car apps, but the public API does not establish which source Google Maps used in this incident. Mirage's accepted mock writes do not prove the location shown by another application or a head unit.

Ordinary apps targeting Android 10 or newer cannot enable or disable Wi-Fi. Mirage targets API 34. There is no supported ordinary-app switch that can force Wi-Fi off and keep it off. No root, device-owner provisioning, accessibility click automation, permission escalation or hidden settings change is introduced. The app can explain the limit and open the system Wi-Fi settings for the user.

The recovery change adds bounded, coalesced retry after transient fused failures and fresh real-location readback, with lifecycle ownership so stale completions cannot revive a stopped run. Fused mock acceptance and observed readback are distinct signals. Cached observations predating the current run must not be treated as a new leak. Persistent failures remain visible rather than being reported as healthy. Replacing an active trip first emits a holding anchor from its last output before publishing the next route, with fresh verification still required.

Underlying Google location tasks are not cancellable. Mode changes are serialized across service instances; overdue enable requests trigger a best-effort urgent disable on Stop and ordered compensation if they complete later. A permanently unresponsive mode task can delay a later Start. The app bounds retries and retires callbacks, but cannot guarantee Google service completion or immediate location restoration in other clients. Real-location restoration is reported only after an actual non-mock readback.

Sources: [Android Wi-Fi toggle restrictions](https://developer.android.com/about/versions/10/privacy/changes#enable-disable-wifi), [Google fused mock mode](https://developers.google.com/android/reference/com/google/android/gms/location/FusedLocationProviderClient#setMockMode(boolean)), [car hardware location APIs](https://developer.android.com/training/cars/apps/library/car-hardware-api), and [Android Auto connection requirements](https://support.google.com/androidauto/answer/6348029).
